# project-tutor-for-intern

面向实习生、新入职开发者和临时接手陌生项目的代码库带教 Skill。

它不会只把目录和类名重新念一遍，而是从“这个项目解决什么问题”开始，逐步建立业务、架构、模块和代码之间的关系，并把关键结论落到真实文件、符号、配置、测试或项目文档上。遇到设计原因或演进问题时，还可以按需结合限定范围的 Git 历史解释“为什么变成现在这样”。

## 一句话定位

当你需要**在对话中读懂一个现有项目**，而不是立即修改代码或生成正式文档时，使用 `$project-tutor-for-intern`。

| 输入 | 默认产出 |
| --- | --- |
| 一个代码库、模块、文件、符号、请求链路或报错 | 对话式导读、代码定位、证据、阅读顺序和下一步建议 |

## 适用人群

- 第一次接触团队代码库的实习生或新人。
- 需要快速理解其他团队模块的开发者。
- 接手缺少文档的遗留项目维护者。
- 准备修改需求，但还不确定影响范围的人。
- 遇到异常，希望先定位根因而不是盲目改代码的人。
- 需要制定阶段性代码阅读计划的带教者或学习者。

## 推荐使用场景

### 1. 从零建立项目全景

适合入职第一天、首次打开大型仓库或完全不知道从哪里开始阅读的情况。

Skill 会优先帮助你确认：

- 项目或当前仓库大致解决什么问题。
- 主要入口、核心模块和上下游关系。
- 一条代表性业务或系统主链路。
- 最值得先看的 3–5 个文件。
- 哪些结论已经确认，哪些仍需要维护者说明。

### 2. 深入理解单个模块

适合“这个目录是干什么的”“为什么需要这一层”“谁在调用这个类”等问题。

Skill 会检查：

- 模块公开入口和职责边界。
- 直接调用方与下游依赖。
- 核心数据结构、配置和测试。
- 主流程、关键分支、失败路径和扩展点。
- 初学者容易产生的误解。

### 3. 追踪完整调用链

适合从一个接口、命令、事件或用户操作出发追踪代码。

每一跳通常包括：

- 文件与符号。
- 输入、处理与输出。
- 条件分支和错误出口。
- 数据或状态变化。
- 支持当前结论的测试、配置或文档证据。

### 4. 改需求前评估影响

适合准备修改校验规则、共享模型、接口、配置或公共组件之前使用。

Skill 会搜索：

- 直接调用方和接口实现。
- 共享数据结构和序列化格式。
- 配置定义与使用点。
- 测试、生成文件、迁移脚本和部署配置。
- 可能无法通过静态搜索发现的动态依赖。

输出重点是最小改动路径、验证范围和剩余风险，而不是武断地承诺“只影响这些文件”。

### 5. 诊断报错或异常行为

适合编译失败、启动失败、请求异常、测试失败、超时或环境差异问题。

默认采用：

```text
现象 → 可复现条件 → 定位 → 假设 → 安全验证 → 根因
```

诊断默认只读。只有用户明确要求修复时，才进入代码修改阶段。

### 6. 制定学习和阅读计划

适合希望在数天或数周内逐步熟悉项目，但不想机械地“读完所有代码”的情况。

计划会围绕可验证目标组织，例如：

- 能运行和定位入口。
- 能画出核心模块地图。
- 能追踪一条代表性主链路。
- 能深入一个与当前任务相关的模块。
- 能在明确影响范围后完成低风险改动。

### 7. 追溯模块或文件的演进

适合“`auth` 为什么这样设计”“这个文件怎么演化来的”“某模块经历过哪些关键重构”等问题。

Skill 会先理解当前实现，再限定到目标模块、文件和少量关键锚点，筛选能解释当前结构的历史节点，重点回答：

- 最早可确认它解决的问题。
- 形成当前结构的关键变化及可观察代价。
- 哪些约束仍被当前代码或测试保护。
- 哪些结论只是推测、候选风险或仍需维护者确认。

普通“这个模块做什么”不会触发 Git 扫描。

## 不适用场景

- 需要直接创建正式教程文档：使用 `$writing-tutorials`。
- 已经明确要求实现功能或修复 Bug：应进入对应开发流程，本 Skill 可先用于定位，但不替代实现。
- 需要完整安全审计、性能压测或生产事故响应：本 Skill 只能提供代码理解和初步分析。
- 只想查询一个通用编程概念，且不涉及当前代码库：直接提问通常更合适。
- 希望从仓库推断真实商业背景：仓库没有证据时，Skill 不会编造业务事实。

## 核心能力

| 能力 | 作用 |
| --- | --- |
| 项目鸟瞰 | 识别入口、核心模块、项目形态和代表性主链路 |
| 业务到代码映射 | 将用户操作或系统任务对应到文件、符号和数据变化 |
| 模块边界分析 | 说明模块为什么存在、谁调用、依赖谁、负责到哪里为止 |
| 调用链追踪 | 从入口逐跳追踪到结果、持久化或外部依赖 |
| 阅读顺序推荐 | 根据当前目标推荐优先文件，而不是要求读完整个仓库 |
| 改动影响分析 | 搜索调用方、共享契约、配置、测试和动态依赖风险 |
| 故障定位 | 用证据驱动的假设逐步缩小异常范围 |
| Git 演进分析 | 按需追踪模块或文件的起点、关键重构、设计原因和当前护栏 |
| 术语教学 | 用准确解释和有限类比帮助新人建立直觉 |
| 学习计划 | 把“熟悉项目”拆成阶段目标、练习和验证标准 |

## 工作方法

### 四层渐进

1. **鸟瞰层**：项目目标、主要入口和核心模块。
2. **业务层**：代表性场景、数据流和状态变化。
3. **模块层**：职责边界、调用关系和扩展点。
4. **代码层**：关键文件、符号、分支、配置和测试。

这四层按需使用，不要求每次全部展开。一个函数级问题可以直接进入代码层；“从零开始”则默认从鸟瞰层开始。

### 证据分级

所有关键判断分成三类：

| 状态 | 含义 |
| --- | --- |
| 已确认 | 由代码、配置、测试或项目文档直接支持 |
| 推测 | 根据命名、结构或常见模式推断，并说明推断依据 |
| 未知 | 仓库内找不到足够证据，需要维护者或业务方确认 |

### 按需可视化

只有在以下情况中才建议使用 Mermaid：

- 三个以上模块之间存在重要关系。
- 请求链路超过三跳。
- 存在状态机、异步事件或多个分支。
- 需要解释某个模块在整体系统中的位置。

简单函数、配置项或两层调用关系优先使用短段落或小表格。

## 推荐调用方式

两个 Skill 的触发范围存在少量重叠，因此推荐显式指定：

```text
使用 $project-tutor-for-intern ……
```

### 通用输入模板

```text
使用 $project-tutor-for-intern。

我的背景：{熟悉的语言、框架或业务程度}
分析范围：{整个项目 / 模块路径 / 文件 / 符号 / 请求链路}
当前目标：{建立认知 / 改需求前定位 / 排错 / 影响分析 / 学习计划}
希望重点：{架构、业务、数据流、失败路径、测试等}
操作边界：只读分析，不要修改代码。

请区分已确认事实、推测和未知项，并为关键结论标出文件和符号。
```

不需要填满所有字段。范围和目标清楚时，Skill 会直接开始。

## 使用示例

### 示例 A：新人完整导读

```text
使用 $project-tutor-for-intern。

我是刚加入项目的实习生，熟悉 TypeScript，但不了解当前业务。
请从零带我理解整个仓库，先不要修改代码。

请包含：
- 一句话项目定位
- 核心模块及职责
- 一张必要时才使用的项目全景图
- 一条代表性请求链路
- 推荐先读的 5 个文件
- 新人容易踩的坑
- 一个验证理解的小任务
```

### 示例 B：模块深潜

```text
使用 $project-tutor-for-intern，深入讲解 src/order 模块。

重点回答：
- 为什么需要这个模块
- 谁调用它、它调用谁
- 入口和核心对象在哪里
- 正常路径和失败路径分别怎样运行
- 哪些测试最值得先看

只读分析，并标记推测内容。
```

### 示例 C：业务链路追踪

```text
使用 $project-tutor-for-intern，追踪“用户提交订单”从入口到最终结果的完整链路。

每一跳标出文件、函数、输入、输出、关键分支和证据。
如果存在异步处理，请区分同步返回和最终状态变化。
```

### 示例 D：改动影响分析

```text
使用 $project-tutor-for-intern。

我准备修改 src/order/validator.ts 中的校验规则。
请先分析直接调用方、共享模型、配置、测试、上下游兼容性和动态依赖风险。
给出最小改动路径与验证清单，暂时不要修改代码。
```

### 示例 E：故障定位

```text
使用 $project-tutor-for-intern，诊断下面的问题。

现象：{错误表现}
触发操作：{如何复现}
期望行为：{本应发生什么}
错误信息：{完整堆栈或日志}

请按“现象 → 定位 → 假设 → 验证 → 根因”分析。
不要修改配置、安装依赖或编辑代码。
```

### 示例 F：学习计划

```text
使用 $project-tutor-for-intern，为我制定两周项目学习计划。

我的背景：熟悉前端开发，但后端经验有限。
当前目标：两周后能独立修改一个低风险需求。

请把每天目标对应到具体文件、练习任务和验证标准，不要只给通用建议。
```

### 示例 G：结合 Git 解释模块演进

```text
使用 $project-tutor-for-intern，结合 Git 历史讲解 src/auth 模块。

重点回答：
- 它最开始解决什么问题
- 哪些关键提交让它逐渐变成现在这样
- 每次主要变化解决了什么、带来什么代价
- 哪些设计仍由当前代码或测试保护，修改时不要轻易破坏

只分析该模块及必要的入口、模型和测试。请区分作者声明、可观察演进、推测和未知，不要逐条复述提交记录。
```

对照：如果只问“`src/auth` 模块做什么”，Skill 默认只研究当前代码，不查看 Git 历史。

## 可能的输出形态

根据请求选择最小充分结构：

| 请求 | 典型输出 |
| --- | --- |
| 全局导读 | 项目定位、核心模块、主链路、阅读顺序、未知项 |
| 模块讲解 | 职责、调用关系、核心对象、测试、扩展点、易错点 |
| 链路追踪 | 逐跳文件与符号、数据变化、分支、失败路径 |
| 影响分析 | 直接影响、共享契约、动态风险、最小改动路径、验证清单 |
| 故障定位 | 现象、证据、候选根因、排除项、下一步安全验证 |
| 演进讲解 | 当前职责、最初问题、关键里程碑、当前设计护栏、未知项 |
| 学习计划 | 阶段目标、阅读对象、实操任务和自检标准 |

如果希望获得更完整、更接近课程式的输出，需要在提示中明确要求架构图、模块表、阅读计划、练习题等内容。

## 能力边界

- 默认只读；讲解或诊断不等于授权修改代码。
- 静态搜索无法保证覆盖运行时注册、反射、动态导入和仓库外消费者。
- 设计理由只有在设计文档、注释、测试或提交记录支持时才能视为已确认。
- Git 历史默认关闭；只有演进型提问或当前证据无法解释关键设计原因时才按目标范围启用。
- 历史分析只读，不自动 fetch、切换分支、扫描所有引用或创建提交。
- 无法仅凭代码准确还原组织流程、商业策略和历史决策。
- 不展示密钥、令牌、密码、连接串、用户数据或不必要的内部地址。
- 不替代人工代码评审、架构评审、安全审计或生产验证。
- 类比用于建立直觉，不替代精确定义和当前项目行为。

## 与 writing-tutorials 配合

推荐工作流：

1. 使用 `$project-tutor-for-intern` 确认范围、主链路、关键文件和未知项。
2. 对重要推测向维护者或业务方求证。
3. 使用 `$writing-tutorials` 将已经确认的结果写入正式教程。

示例：

```text
先使用 $project-tutor-for-intern，只读分析 src/workflow 模块。
确认完成后，再使用 $writing-tutorials 把结论写成单文件教程，保留已确认、推测和未知的区分。
```

## 常见问题

### 会自动修改代码吗？

不会。默认只读。只有用户明确要求实现或修复时，才应进入代码编辑流程。

### 每次都会画图吗？

不会。只有复杂依赖、长调用链、状态机或异步流程确实适合可视化时才画图。

### 能保证业务解释完全正确吗？

不能。Skill 会尽量从代码、测试和文档取证，并明确标出推测和未知项。

### 可以用它生成入职教程吗？

可以先用它研究和讲解；如果需要把结果落盘成长期维护的教程，建议再交给 `$writing-tutorials`。

### 每次都会查看 Git 历史吗？

不会。解释当前模块职责、调用链或文件行为时默认只看当前代码。只有用户询问设计原因、演进、文件历史、重构过程，或当前证据不足以解释关键原因时，才会在目标范围内补查 Git。
