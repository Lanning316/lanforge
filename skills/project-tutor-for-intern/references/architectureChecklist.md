# 架构导读检查清单

在用户需要全局导读、模块地图或阅读顺序时使用。按问题范围选择条目，不要为了填满清单而扩大分析。

## 证据记录

先建立一张简短证据表：

| 结论 | 状态 | 依据 |
| --- | --- | --- |
| 项目定位或模块职责 | 已确认 / 推测 / 未知 | 文档、代码、配置、测试或命名依据 |

- **已确认**：仓库有直接证据。
- **推测**：根据结构或命名推断，必须说明推断依据。
- **未知**：需要维护者或业务方确认。

## 1. 项目定位

- [ ] 用一句话说明项目或当前模块做什么。
- [ ] 找到目标用户或调用方的仓库证据；找不到时标为未知。
- [ ] 列出 1–3 个核心场景，区分已确认和推测。
- [ ] 说明本仓库与上下游系统的已知关系。

## 2. 技术栈与项目形态

- [ ] 从依赖清单、构建文件和目录结构确认语言、框架和构建工具。
- [ ] 判断单体、服务化、多包仓库、前后端分离或插件式结构。
- [ ] 定位部署、容器或运行配置；不要只凭文件名断言生产架构。
- [ ] 区分项目自有代码、生成代码、第三方依赖和示例代码。

## 3. 入口与启动

- [ ] 找到可执行入口、命令注册、路由注册或框架启动位置。
- [ ] 说明配置加载、依赖初始化、中间件注册和资源清理的顺序。
- [ ] 从项目文档或脚本确认最小启动方式。
- [ ] 标注启动流程中仍依赖外部环境的部分。

## 4. 核心模块

- [ ] 识别 3–7 个核心模块并写出一句话职责。
- [ ] 找到模块公开入口和主要调用方。
- [ ] 说明模块的下游依赖和数据边界。
- [ ] 按当前学习目标标记“先看”“随后看”“用到再看”。
- [ ] 避免仅按目录名推断职责；抽查实现或测试。

## 5. 代表性主链路

- [ ] 选择一个最常见且有证据的用户操作或系统任务。
- [ ] 从入口追踪到结果，记录每一跳的文件和符号。
- [ ] 标注输入、输出、关键数据变化和错误出口。
- [ ] 区分主干逻辑与日志、指标、缓存、重试等辅助逻辑。
- [ ] 三跳以上或分支较多时再绘制流程图或序列图。

## 6. 配置与数据

- [ ] 找到配置定义、加载和使用位置。
- [ ] 从代码或官方文档确认配置优先级，不套用固定顺序。
- [ ] 区分开发、测试和生产配置，但不展示敏感值。
- [ ] 说明数据来源、持久化位置、缓存和临时状态。
- [ ] 标注共享结构、序列化格式或数据库模式的兼容性风险。

## 7. 测试与质量信号

- [ ] 找到与主链路对应的单元测试、集成测试或端到端测试。
- [ ] 从测试用例确认正常路径、边界条件和错误处理。
- [ ] 找到格式化、静态检查、构建和测试命令。
- [ ] 若缺少测试，明确说明影响分析的可信度限制。

## 8. 扩展点与影响范围

- [ ] 找到新增接口、处理器、插件或业务规则的已有范例。
- [ ] 搜索直接调用方、实现类、共享模型和配置使用点。
- [ ] 检查生成文件、迁移脚本、文档和部署配置是否需要同步。
- [ ] 给出最小改动路径和验证清单，不承诺静态搜索能覆盖动态依赖。

## 9. 推荐阅读顺序

- [ ] 推荐 3–5 个具体文件或目录。
- [ ] 每项说明阅读目的，而不虚构精确耗时。
- [ ] 给出一个能验证理解的小任务。
- [ ] 列出需要向维护者确认的 1–3 个问题。
