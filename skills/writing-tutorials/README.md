# writing-tutorials

[返回 Skills 索引](../README.md) · [返回仓库总览](../../README.md)

把现有代码、模块或架构写成可验证、可维护的 Markdown 技术教程。

它面向需要长期沉淀知识的团队和学习者：先研究真实源码、测试、配置与项目文档，再组织教学主线、源码定位、设计权衡、失败路径和阅读路线；遇到设计原因或演进问题时，可按需结合限定范围的 Git 历史解释“为什么变成现在这样”。

## 一句话定位

当你需要**在项目中创建或更新正式技术教程文件**时，使用 `$writing-tutorials`。

| 输入 | 默认产出 |
| --- | --- |
| 一个现有代码库、模块、目录、文件组或架构主题 | 一份以源码证据为基础的 Markdown 教程 |

如果只想在对话中理解代码，不需要创建文件，优先使用 `$project-tutor-for-intern`。

## 适用人群

- 为新成员准备入门材料的开发者或带教者。
- 希望把复杂模块讲清楚并长期维护的模块负责人。
- 接手遗留代码，需要补齐知识文档的维护者。
- 准备内部技术分享、学习材料或面试复习资料的开发者。
- 希望把已有零散笔记整理成源码可追溯教程的团队。
- 需要随着代码变化更新现有教程的人。

## 推荐使用场景

### 1. 为单个模块写入门教程

适合缓存、订单、搜索、调度、权限、工作流等边界相对明确的模块。

教程通常覆盖：

- 模块解决的问题和适用范围。
- 在系统中的位置。
- 入口与代表性主流程。
- 核心对象和职责边界。
- 失败路径、常见坑和扩展点。
- 源码索引与未确认项。

### 2. 为新成员生成代码阅读指南

适合把“从哪里开始读”沉淀成仓库文档。

可包含：

- 不同经验读者的阅读路线。
- 推荐阅读顺序。
- 每个核心文件的作用。
- 从入口到结果的代码路径。
- 理解检查或练习任务。

### 3. 把复杂架构拆成多章节教程

适合模块较大、机制较多或需要长期维护的主题。

可以按需生成：

- README 导航。
- 入门介绍。
- 架构全景。
- 多个核心机制章节。
- 面试 Q&A 附录。
- 源码索引附录。

多文件不是默认行为，必须由用户明确要求。

### 4. 生成面试导向的项目拆解

适合希望理解“本项目实际怎么做”，而不是背诵教科书定义的场景。

面试内容可以分为：

- 基础理解：模块做什么、为什么存在、有哪些组件。
- 实现原理：主流程、关键算法、数据边界和设计权衡。
- 故障与演进：依赖失败、扩展限制、当前缺陷和重构方向。

每个核心回答都应尽量关联源码、测试或项目文档，并避免鼓励读者虚构个人贡献。

### 5. 更新已有教程

适合代码重构、文件移动、接口变化或旧链接失效后维护文档。

Skill 可以：

- 对照当前代码检查旧教程。
- 更新路径、符号和主流程。
- 标记已经失效的设计描述。
- 保留仍然正确的内容，避免整篇重写。
- 重新运行确定性校验和人工验收。

### 6. 采用规格与计划驱动的正式写作

适合大型教程、多人评审或需要阶段性确认的工作。

可以显式启用：

```text
_spec.md → 用户确认 → _plan.md → 用户确认 → 正文 → 校验
```

规格和计划不会默认生成，避免在普通教程任务中增加无用文件。

### 7. 编写模块或文件演进教程

适合“结合 Git 讲 `auth` 模块”“记录某文件的历史”“解释某模块的重构过程”等需要沉淀设计背景的场景。

历史模式先研究当前实现，再筛选少量关键提交，回答最初问题、关键里程碑、当前设计的形成过程和修改护栏。普通模块教程不会扫描 Git，也不会保留历史章节。

## 不适用场景

- 只想问一个函数或模块如何工作：使用 `$project-tutor-for-intern` 或直接提问。
- 需要生成 API 参考手册、接口字段字典或自动化参考文档：应使用更适合结构化 API 的工具。
- 只需要修改 README、变更日志或发布说明：本 Skill 的深度教程流程可能过重。
- 需要产品介绍、市场文案或面向非技术决策者的说明：教程结构并不适合。
- 需要自动上传 Wiki、发布网站、推送远程仓库：本 Skill 默认不执行这些外部操作。
- 目标代码尚不存在：本 Skill 主要解释现有实现，不负责从需求直接设计完整系统。

## 核心能力

| 能力 | 作用 |
| --- | --- |
| 源码研究 | 定位入口、调用方、下游依赖、配置、测试和失败路径 |
| 多层读者设计 | 为新人、有经验开发者和速查读者提供不同阅读路线 |
| 教学主线 | 用具体场景、连续步骤和源码证据讲清核心机制 |
| 设计与实现区分 | 有证据时解释设计决策，无证据时标为实现观察或推测 |
| Git 演进写作 | 按需将模块起点、关键重构、当前护栏和未知项写入教程 |
| 可移植引用 | 按项目约定和阅读环境使用相对链接、平台链接或可搜索的文本定位 |
| 单文件教程 | 用一份文档交付完整主题，默认推荐 |
| 多文件教程 | 为大型主题生成导航、章节和可选附录 |
| 面试拆解 | 按用户要求生成项目证据驱动的 Q&A |
| 确定性校验 | 检查占位符、围栏、路径、链接、源码定位和总结位置 |
| 人工整体验收 | 检查事实、术语、主线、受众、安全和维护性 |

## 默认行为

默认遵循最小充分产出：

- 沿用项目已有文档目录约定。
- 没有约定时写入 `docs/learn/<topic>/<topic>.md`。
- 只生成一份单文件教程。
- 不生成 `_spec.md` 和 `_plan.md`。
- 不生成面试 Q&A。
- 不要求 Git 仓库。
- 不为普通教程扫描 Git 或生成“演进与设计意图”章节。
- 不自动 commit、push 或发布。
- 不修改目标模块源码。

这些可选产出没有被删除；需要时按相应触发条件启用。历史模式也可在当前证据不足以解释关键设计理由时自动启用，但会先说明原因和扫描范围。

## 三种产出模式

### 模式 A：默认单文件

```text
docs/learn/<topic>/
└── <topic>.md
```

适合绝大多数边界明确的模块。优点是阅读连续、链接简单、维护成本低。

### 模式 B：受控单文件

```text
docs/learn/<topic>/
├── _spec.md
├── _plan.md
└── <topic>.md
```

适合需要先确认范围、受众和验收标准的正式写作任务。

### 模式 C：多文件教程

```text
docs/learn/<topic>/
├── README.md
├── 00-intro.md
├── 01-overview.md
├── 02-<chapter>.md
├── 03-<chapter>.md
├── appendix-a-interview-qa.md   # 可选
└── appendix-b-code-index.md     # 可选
```

章节数量和附录根据主题决定，不为了凑齐目录创建空洞文件。

## 工作流程

### 1. 探测项目

只读确认：

- 目标模块是否存在。
- 主语言、构建方式和文档目录约定。
- 是否存在测试、示例、设计文档和可用的版本信息。
- 项目已有的源码引用方式，以及教程最终的阅读环境。

Git 是可选信息源，不是使用前提。只有用户询问设计原因、演进、文件历史、重构过程，或当前证据不足以解释关键设计理由时才启用历史模式；开始前说明会补查目标范围内的历史。

### 2. 确认真正影响产物的决策

优先从请求和仓库推断：

- 教程主题和代码范围。
- 主要读者。
- 单文件或多文件。
- 是否需要面试 Q&A。
- 输出目录与语言。

信息足够时直接开始，不进行固定六轮问答。

### 3. 研究源码

在写作前定位：

- 公开入口和核心对象。
- 一条代表性主流程。
- 直接调用方和下游依赖。
- 配置、测试、错误路径和扩展点。
- 有证据的设计决策与仍未知的问题。

历史模式启用时，从入口、核心模型和关键测试反向筛选能解释当前结构的少量里程碑；不默认扫描全仓库、所有分支或远程历史。

### 4. 选择并填写模板

根据产出模式按需读取 `templates/` 下的 Markdown 模板。模板是结构起点，不是必须逐节填满的表格。

### 5. 运行校验

先运行确定性校验器，再执行人工语义验收。发现问题后修正文档并重新校验。

### 6. 可选 Git 操作

只有用户明确要求时才提交。不会创建空提交，也不会自动推送。

## 五部分教学节奏

### 单文件模式

整份教程整体覆盖：

1. 具体场景或类比。
2. 一步步主流程。
3. 可验证源码证据。
4. 按需补充的知识框。
5. 文末一个“💡 一句话记住”。

### 多文件模式

每个实质性教学章节采用相同节奏，并在章末保留一个总结。README、规格、计划和附录不要求使用该节奏。

知识框、图表、链接和篇幅都不设固定数量。是否加入取决于实际教学价值。

## 源码引用策略

Skill 不预设代码托管平台或固定链接优先级。它先沿用项目已有文档约定，再根据教程的阅读环境、目标读者权限和维护方式选择：

- 项目内相对链接。
- 代码托管平台或文档系统链接。
- 仓库相对路径与符号名。
- 测试名、配置键、文档章节或其他项目原生标识。
- 确有帮助时的行号范围。

固定到某个版本的链接适合复现、审计和历史说明；跟随当前版本的链接适合持续维护的活文档。只有需要区分版本或项目规范要求时，才记录提交、标签、版本号或工作区状态。

历史节点使用短提交哈希、日期、主题和相关路径定位。它们用于核实演进结论，不自动意味着整篇教程固定在该提交。

默认禁止 `file:///`、用户主目录和机器特有的绝对路径等不可移植定位。


```text
使用 $writing-tutorials。

目标代码：{模块路径、文件组或主题}
教程目标：{新人入门 / 内部维护 / 深度原理 / 面试准备 / 更新旧教程}
主要读者：{新人 / 有经验开发者 / 资深开发者 / 混合读者}

```

不需要填写所有字段。最少提供目标代码和教程目标即可。

## 使用示例

### 示例 A：默认单文件教程

```text
使用 $writing-tutorials。

为 src/cache 模块生成一份面向新成员的单文件教程。
重点解释入口、主流程、职责边界、失败路径和扩展点。
沿用项目现有 docs 目录，自动选择可移植源码链接。
不要生成 spec、plan 和面试题，不要提交 Git。
```

### 示例 B：多层读者教程

```text
使用 $writing-tutorials，为 src/search 模块写一份单文件教程。

主要读者是刚入职的后端开发者，同时提供资深开发者速查路线。
新人主线需要解释领域术语；速查路线重点覆盖架构边界、设计权衡、失败路径和源码索引。
不要提交 Git。
```

### 示例 C：受控写作流程

```text
使用 $writing-tutorials，为 payment 模块编写正式教程。

采用受控流程：
1. 先生成 _spec.md，等待我确认
2. 确认后生成 _plan.md
3. 再编写单文件正文
4. 运行校验并报告结果

未经我确认不要提交 Git。
```

### 示例 D：多文件大型教程

```text
使用 $writing-tutorials，为 src/workflow 模块生成多文件教程。

要求包含：
- README 导航
- 入门介绍
- 架构全景
- 三个核心机制章节
- 源码索引附录

不需要面试 Q&A，不提交 Git。
```

### 示例 E：面试导向教程

```text
使用 $writing-tutorials，为 scheduler 模块生成面试导向教程。

除主流程和设计决策外，增加：
- 基础理解 5 题
- 实现原理 8 题
- 故障与演进 5 题

每个核心回答必须有代码、测试或项目文档证据。
不要虚构设计背景或个人贡献。
```

### 示例 F：更新已有教程

```text
使用 $writing-tutorials，更新 docs/learn/search/search.md。

对照当前 src/search 代码检查：
- 失效链接和漂移行号
- 已经变更的主流程
- 重命名的对象和术语
- 已删除或新增的失败路径

保留仍然正确的内容，完成后运行校验，不提交 Git。
```

### 示例 G：校验后提交

```text
使用 $writing-tutorials，为 src/auth 生成单文件教程。

先完成源码研究、文档写作和校验。
确认只包含本教程相关文件后，创建一个符合仓库规范的 Git 提交，但不要 push。
```

### 示例 H：结合 Git 编写演进教程

```text
使用 $writing-tutorials，为 src/auth 生成面向新人的单文件教程，并启用 Git 历史模式。

除当前职责、入口和主流程外，重点说明：
- 最早可确认它解决的问题
- 形成当前结构的关键里程碑
- 每次主要变化解决的问题与可观察代价
- 当前仍由代码或测试保护、修改时不要轻易破坏的设计护栏

每个历史节点记录短提交哈希、日期、主题和相关路径。区分作者声明、可观察演进、推测和未知，不要写成逐提交变更日志，也不要提交 Git。
```

对照：普通“为 `src/auth` 写入门教程”默认不扫描 Git，模板中的“演进与设计意图”章节会被删除。

## 模板目录

所有模板都是普通 Markdown 文件：

| 模板 | 用途 |
| --- | --- |
| `templates/tutorial.md` | 默认单文件整合教程 |
| `templates/_spec.md` | 可选教程规格 |
| `templates/_plan.md` | 可选实施计划 |
| `templates/README.md` | 多文件教程导航 |
| `templates/00-intro.md` | 多文件教程入门章 |
| `templates/01-overview.md` | 多文件教程全景章 |
| `templates/chapter.md` | 核心机制章节 |
| `templates/appendix-a-interview-qa.md` | 可选面试 Q&A |
| `templates/appendix-b-code-index.md` | 可选源码索引 |

模板中的占位符、填写提示和不适用章节必须在交付前删除。

## 校验方式

### 确定性校验

Skill 提供无第三方依赖的跨平台 Python 校验器：

```text
python scripts/validate_tutorial.py <tutorial.md> --repo-root <project-root>
```

可选模式：

```text
--mode single
--mode chapter
--mode appendix
```

校验器检查：

- 模板占位符。
- Markdown 围栏是否闭合。
- `file:///` 和本机绝对路径。
- 本地相对链接是否存在、是否逃出项目根目录。
- 源码定位是否存在。
- “💡 一句话记住”的数量和位置。
- 常见核心结构缺失警告。

运行自测：

```text
python scripts/validate_tutorial.py --self-test
```

### 人工语义验收

脚本无法判断“这段代码是否真的支持这句话”，因此还需要检查：

- 主流程是否完整且没有跳步。
- 设计理由是否有证据。
- 历史模式是否只在满足触发条件时出现。
- 历史事实、动机推断和设计护栏是否分别有足够证据。
- 推测和未知项是否明确。
- 阅读路线与实际标题是否一致。
- 术语、对象名称和职责描述是否统一。
- Q&A 是否引入正文未解释的概念。
- 是否泄露敏感信息或内部个人路径。

## Git 与文件操作边界

- 写教程文件属于本 Skill 的正常行为。
- 默认不修改目标模块源码。
- 默认不生成 `_spec.md` 和 `_plan.md`。
- 默认不扫描 Git 历史；历史模式也只读取限定范围的本地可达历史。
- 默认不 commit、push、发布或上传。
- 不自动 fetch、切换分支或扫描所有引用。
- 只有用户明确要求时才执行 Git 操作。
- 不创建空提交。
- 提交前确认不包含用户的无关改动。
- 用户中途取消时，保留已经创建的文件，但不擅自提交。

## 能力边界

- 教程质量受目标代码、测试和项目文档完整度影响。
- 无法从代码证明的业务背景和历史决策必须标为未知或推测。
- 浅克隆、squash、历史重写或贫乏提交说明会限制演进结论；不要把“最早可见状态”写成绝对起点。
- 只有历史证据和当前代码、测试或契约共同支持时，才把某项称为“不应轻易破坏的设计护栏”。
- 源码相对链接可验证文件存在，但不能保证每个 Markdown 渲染器都支持同样的锚点或跳转行为。
- 外部或内部平台不可访问时，只能报告链接未验证，不能推断其内容。
- 固定行数、图表数和知识框数不代表教程质量，因此不作为硬门槛。
- Skill 不替代技术负责人对架构意图和业务事实的确认。
- Skill 不负责自动发布到 Wiki、文档站或远程仓库。
- Skill 不负责生成与现有代码无关的完整系统设计。

## 与 project-tutor-for-intern 配合

重要或陌生模块推荐先研究、后落盘：

1. 使用 `$project-tutor-for-intern` 在对话中确认范围、主流程和未知项。
2. 必要时让维护者确认关键推测。
3. 使用 `$writing-tutorials` 将结论写成正式教程。

```text
第一步：
使用 $project-tutor-for-intern，只读分析 src/workflow 模块。

第二步：
使用 $writing-tutorials，把刚才确认的内容写成单文件教程，保留事实、推测和未知的区分。
```

如果范围已经非常明确，也可以直接使用本 Skill，它会自行完成必要的源码研究。

## 安装

在支持 Skill 目录的环境中，可以复制或链接整个 `writing-tutorials` 目录。

Unix 风格环境可运行：

```bash
./install.sh
```

指定安装根目录：

```bash
SKILL_INSTALL_ROOT=/path/to/skills ./install.sh
```

安装脚本：

- 不覆盖已有真实文件或目录。
- 不替换指向其他位置的 symlink。
- 重复安装到相同来源时安全退出。

卸载：

```bash
./uninstall.sh
```

卸载脚本只移除指向当前 Skill 来源的 symlink。

## 常见问题

### 为什么默认只生成一份正文？

多数模块不需要完整文档集。单文件更容易阅读、链接和维护；大型主题可以显式切换到多文件模式。

### 为什么不再要求固定篇幅？

小模块强行扩写会产生灌水，复杂模块限制行数会遗漏关键内容。当前以范围完整、证据准确和读者可跟随为标准。

### 没有 Git 可以使用吗？

可以。Git 和远程仓库都不是前置条件；Skill 会使用项目中实际可用的文件、符号、测试、配置或文档定位。

### 每篇教程都会扫描 Git 吗？

不会。普通现状教程只研究当前代码。只有用户询问设计原因、演进、文件历史、重构过程，或当前证据无法解释关键设计理由时，才会在目标范围内启用 Git 历史模式。

### 会自动生成面试题吗？

不会。只有用户明确要求面试准备时才生成。

### 会修改代码吗？

默认只读取目标代码并写教程文件，不修改被讲解的源码。

### 可以只更新旧文档中的链接吗？

可以。在请求中明确限定“只更新失效链接和定位，不重写正文”。
