# 技术教程写作

把现有代码研究成一份可验证、可维护、能被不同经验层读者使用的 Markdown 教程。先确认事实，再组织教学；不要为了满足格式指标而扩写无价值内容。

## 使用边界

使用本 Skill：

- 创建或更新讲解现有代码、模块或架构的教程文件。
- 把入口、主流程、职责边界和设计决策连接到源码证据。
- 为不同读者设计阅读路线。

不要用于：

- 只在对话中回答一个代码问题。
- 自动生成 API 参考、变更日志或产品介绍。
- 未经要求发布、上传、提交或推送文档。
- 用模板替代源码研究。

## 产出模式

根据用户请求选择一种模式。

### 默认：单文件教程

只创建：

```text
docs/learn/<topic>/<topic>.md
```

沿用项目已有文档目录约定；只有没有约定时才使用 `docs/learn/<topic>/`。

### 可选：受控写作流程

只有用户明确要求规格评审、分阶段审批或长期维护计划时，额外创建：

```text
_spec.md
_plan.md
<topic>.md
```

使用 `templates/_spec.md` 和 `templates/_plan.md`。规格和计划是用户可见产物，不要默认污染仓库。

### 可选：多文件教程

只有用户明确要求拆章时，使用 README、intro、overview、chapter 和 appendix 模板。根据实际主题决定章节数量，不强制创建空洞章节。

## 工作流

### Phase 1：探测目标环境

先只读检查：

1. 用户指定的模块、文件或符号是否存在。
2. 项目的主语言、构建方式和文档目录约定。
3. 是否有可用于理解行为的测试、示例和设计文档。
4. 项目已有的源码引用方式，以及教程最终会在哪种环境中阅读。

不要假定项目使用 Git、托管在特定代码平台，或读者能够访问远程仓库。普通“为 `auth` 写模块教程”等当前实现请求不扫描 Git。只有以下情况启用 Git 历史模式：

- 用户明确询问“为什么这样设计”“怎么演化来的”“某文件历史”“某模块重构过程”，或要求结合 Git。
- 当前代码、测试、注释和设计文档不足以解释教程中的关键设计原因；开始前用一句话说明将补查目标范围内的历史。

启用后读取 `references/git-history-analysis.md`。历史只覆盖目标模块、文件或关键符号；默认不扫描全仓库、所有分支或远程历史。其他情况下，只有复现、审计或版本差异确实重要时，才记录版本、标签、提交或工作区状态等源码上下文。

### Phase 2：只澄清真正缺失的决策

优先从用户请求和仓库推断：

- 目标模块和教程主题。
- 受众与语言。
- 单文件或多文件。
- 是否需要面试 Q&A。
- 输出目录。

信息足够时直接开始。只有某个缺失决定会显著改变范围或产物时，才提出一个简短问题。用户要求跳过澄清时，采用以下默认值：

- 单文件教程。
- 兼顾新人和有经验开发者，以新人可跟随为主线。
- 不生成面试 Q&A。
- 不生成 `_spec.md`、`_plan.md`。
- 不创建 Git 提交。

### Phase 3：研究源码并记录证据

在写作前完成最小充分研究：

1. 定位公开入口、核心对象和代表性主流程。
2. 搜索直接调用方、下游依赖、配置和相关测试。
3. 区分主干、异常路径和辅助逻辑。
4. 记录设计决策的直接证据；没有文档、注释、测试或提交记录时，将理由写成推测。
5. 记录未知项，不用通用经验填补项目事实。

每个核心结论至少关联一个文件、符号、测试或项目文档。

Git 历史模式启用时，先确认当前实现，再从入口、核心模型和关键测试反向筛选少量里程碑。历史结论必须区分作者明确声明、可观察演进、推测与未知；只有历史证据和当前约束共同支持时，才将某项写成“不应轻易破坏的设计护栏”。

### Phase 4：设计结构

单文件通常包含：

1. 阅读路线和范围。
2. 类比开场与必要背景。
3. 全景图或简短组件地图。
4. 一步步主流程。
5. 核心对象与职责边界。
6. 有证据的设计决策。
7. Git 历史模式启用时的演进与设计意图。
8. 常见坑、失败路径和扩展点。
9. 可选的理解练习或面试 Q&A。
10. 源码索引和最终一句话记忆。

按主题删减，不要求所有教程机械包含这些章节。没有可靠证据的“设计决策”应改名为“实现观察”或省略。

### Phase 5：写正文

遵循以下规则：

- 每个步骤说明“做什么 → 源码在哪里 → 为什么或依据是什么”。
- 历史章节只保留能解释当前结构的关键里程碑，不写逐提交流水账。
- 历史结论引用短提交哈希、日期、提交主题和相关路径；远程提交链接仅在符合项目约定且读者可访问时使用。
- 代码片段只保留支持当前解释的最小范围。
- 术语首次出现时解释，后文保持同一名称。
- 类比之后指出类比不覆盖的边界。
- 图只用于三个以上组件、三跳以上链路、状态变化或复杂分支。
- 面试 Q&A 仅在用户要求面试准备时加入。
- 不用固定行数、知识框数量或链接数量衡量质量。

### Phase 6：验证

先运行跨平台校验脚本：

```text
python <skill-root>/scripts/validate_tutorial.py <tutorial-path> --repo-root <project-root>
```

如果环境没有 Python，按 `references/quality-validation.md` 手工检查。随后读取 `references/cross-review-checklist.md` 完成语义审查。

校验失败时修正文档并重跑；不要通过灌水、重复链接或无关知识框满足检查。

### Phase 7：可选 Git 操作

只有用户明确要求提交时才执行 Git 操作。提交前：

1. 展示或说明将提交的文档范围。
2. 确认不包含用户的无关改动。
3. 使用与仓库规范一致的提交消息。

不创建空提交，不自动推送，不把“已经写完”与“已经提交”绑定。

## 教学节奏

采用五部分节奏，但区分产出模式：

### 单文件模式

整份教程整体覆盖：

1. 类比或具体场景。
2. 一步步主流程。
3. 源码证据。
4. 按需补充的知识框。
5. 文末恰好一个“💡 一句话记住”。

知识框数量取决于读者确实缺少的背景，不设最低数量。

### 多文件模式

每个实质性教学章节采用相同五部分节奏，并在章末保留一个“💡 一句话记住”。README、导航和附录不受此要求约束。

这样既保留章节级教学节奏，也避免单文件中出现多个互相竞争的总结。

## 源码引用策略

源码引用服务于“读者能找到并验证证据”，不规定统一平台或固定优先级。先沿用项目现有文档约定；没有约定时，根据阅读环境、访问权限和维护方式，在以下形式中选择最合适的一种：

- 项目内可解析的相对链接。
- 代码托管平台或文档系统提供的链接。
- 仓库相对路径、符号名，以及确有帮助时的行号。
- 测试名、配置键、文档章节或其他能稳定定位证据的项目原生标识。

版本、标签或提交仅在用户要求固定版本，或教程需要可复现快照时记录。面向持续更新代码的教程可以使用随项目演进的链接，但不要把可变链接描述成“永久链接”。详细决策见 `references/source-linking.md`。

Git 历史模式中的提交标识用于核实演进证据，不等同于把整篇教程固定到该提交；两种上下文必须明确区分。

默认禁止 `file:///` 和包含用户名的绝对路径。它们不可移植，还可能泄露本机目录信息。

## 质量标准

教程完成时应满足：

- 目标模块、范围和必要的源码上下文清楚。
- 主流程能从入口追踪到结果。
- 关键结论能回到源码、测试或项目文档验证。
- 已确认事实、推测和未知项没有混写。
- 不残留模板占位符或未闭合代码块。
- 链接可移植，且未包含本机绝对路径或敏感信息。
- 阅读路线与实际标题一致。
- Q&A 不引入正文从未解释的概念。
- 最终一句话记忆位于单文件末尾或实质性章节末尾。

## 完成提示

完成后只报告：

- 创建或更新了哪些文件。
- 采用的源码引用方式，以及确有需要时的版本上下文。
- 执行了哪些验证及结果。
- 仍未确认的事实或维护风险。

只有实际执行成功时才声称已经提交或推送。
