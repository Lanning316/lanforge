# 多层读者写作指南

在确定受众、阅读路线和术语深度时使用。不要默认所有教程都必须同时服务三类读者；用户指定单一受众时，以该受众为主。

## 目录

1. 读者画像
2. 单文件共存策略
3. 内容取舍
4. 阅读路线

## 1. 读者画像

| 读者 | 通常已知 | 最需要什么 | 应避免什么 |
| --- | --- | --- | --- |
| 新人 | 基础编程知识 | 术语、业务背景、连续步骤、验证方法 | 跳步和术语堆积 |
| 有经验开发者 | 常见开发与架构模式 | 模块边界、数据流、项目特有决策 | 从基础语法讲起 |
| 资深或速查读者 | 同领域经验 | 差异点、权衡、失败路径和源码入口 | 把关键决策埋在长篇背景里 |

画像只用于决定解释方式，不用于给读者贴能力标签。

## 2. 单文件共存策略

### 主线保持可跟随

主流程写到新人能够连续跟随，但不要重复解释通用语法。每一步固定回答：

1. 这一步做什么。
2. 源码在哪里。
3. 为什么存在或有什么证据。
4. 输入和输出如何变化。

### 背景按需折叠

使用“📦 额外知识”补充确实会阻碍理解的通用背景。知识框不是数量指标；一个小模块可以没有，复杂领域可以有多个。

### 把项目特有决策放在显眼位置

有经验读者最关心：

- 本项目与常见实现有什么不同。
- 选择背后的证据和约束是什么。
- 哪些是明确设计，哪些只是从代码推测。
- 失败时如何表现，扩展时改哪里。

没有证据时使用“实现观察”而不是“设计决策”。

## 3. 内容取舍

| 内容 | 主线 | 知识框 | 可选附录 |
| --- | --- | --- | --- |
| 目标模块的核心机制 | 是 | 否 | 否 |
| 不看就无法继续的术语 | 简短解释 | 可展开 | 否 |
| 通用算法或协议背景 | 简要带过 | 是 | 深入推导 |
| 项目特有权衡 | 是 | 否 | 可汇总 |
| 稀有分支或历史背景 | 否 | 可选 | 可选 |
| 面试问题 | 用户要求时简要加入 | 否 | 用户要求多题时加入 |

删掉与当前学习目标无关的知识，而不是通过附录保存所有内容。

## 4. 阅读路线

阅读路线必须引用教程真实存在的标题，不使用固定章节编号占位。

示例：

| 读者 | 建议路线 |
| --- | --- |
| 新人 | 范围 → 类比 → 全景 → 主流程 → 坑点 → 源码索引 |
| 有经验开发者 | 全景 → 主流程 → 职责边界 → 实现观察或设计决策 |
| 速查读者 | 范围 → 全景 → 决策与失败路径 → 源码索引 |

若教程只面向一种读者，只保留一条路线。

## 自检问题

- 新人是否会在第一个未解释术语处掉队？
- 有经验开发者是否能快速找到边界和权衡？
- 阅读路线中的每个标题是否真实存在？
- 知识框是否真的支持主线，而不是展示作者知道很多？
- 项目特有结论是否有源码、测试、文档或提交证据？
