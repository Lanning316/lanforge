# 可移植源码引用指南

在教程中引用代码、测试、配置或项目文档前使用。目标是让目标读者能够找到并核实证据，同时避免把某一种版本控制系统、托管平台或链接格式写成通用要求。

## 1. 先判断使用环境

先确认以下信息；能从项目约定推断时无需询问用户：

- 教程是在仓库内阅读、文档站发布，还是复制到仓库之外。
- 目标读者是否有权访问相关代码或内部文档。
- 项目已有文档使用相对路径、平台链接、符号引用还是其他格式。
- 教程描述持续演进的代码，还是必须复现某个固定版本。

优先沿用项目已有且可用的引用方式。没有现成约定时，选择维护成本最低、对目标读者最可靠的形式，不必同时提供多套链接。

## 2. 可选引用形式

### 项目内相对链接

适合教程与源码一起维护、渲染器能解析相对路径的场景。链接应相对于教程文件计算，并保持在项目边界内。链接文字可以使用文件名或能帮助读者识别目标的简短说明。

如果渲染器不支持跳转到代码行，可以在链接旁补充仓库相对路径或符号名。不要为了统一格式强制添加行号。

### 平台或文档系统链接

适合教程发布在仓库之外，或团队已有代码浏览平台、文档系统、符号索引时。直接使用项目实际支持的 URL 或标识，不推测平台域名和 URL 规则。

固定到提交、标签或版本的链接适合审计、复现和历史说明；跟随默认分支或当前版本的链接适合与代码同步维护的活文档。应准确描述其稳定性，不要把会随代码变化的链接称为“永久链接”。

仅在目标读者本来就有访问权限时引用私有地址，并避免在公开产物中暴露内部主机名或资源标识。

### 纯文本定位

无法生成可靠链接时，使用项目原生的可搜索定位信息，例如：

- 仓库相对路径与符号名。
- 测试文件与测试用例名。
- 配置文件与配置键。
- 模块、包、类、函数或文档章节标识。
- 确有帮助且维护成本可接受时的行号范围。

路径加符号通常比单独的行号更耐久。对于生成代码、单文件脚本或没有符号系统的内容，行号可能仍是合理选择。

## 3. 版本上下文

版本信息不是每篇教程的必填项。仅在以下情况记录提交、标签、版本号、发布日期或“当前工作区快照”等上下文：

- 用户要求教程对应固定版本。
- 不同版本行为明显不同。
- 复现、审计或长期归档需要精确快照。
- 项目已有文档规范要求记录。

记录最能帮助读者复现内容的上下文，不要仅因为 Git 信息可用就强制写入 commit。

## 4. 历史证据定位

Git 历史模式中的提交标识用于核实某个演进结论，不自动意味着整篇教程固定在该提交。每个关键节点至少记录短提交哈希、日期、提交主题和相关路径。

- 项目已有可访问的远程提交链接约定时，可以沿用该链接形式。
- 无法确认远程地址或读者权限时，使用本地可搜索的提交标识，不猜测托管平台 URL。
- 当前实现的源码链接继续指向教程声明的当前版本；历史提交只支持相应的历史事实。
- 浅克隆、squash 或历史重写导致证据不完整时，在正文中记录限制。

## 5. 安全与可移植性

默认不要写入：

- `file:///...` 形式的本机文件链接。
- 包含用户名、用户主目录或机器特有目录的绝对路径。
- 读者无权访问且会暴露内部结构的私有地址。
- 无法确认格式却根据某个平台猜出的 URL。
- 只有模糊文件描述、无法搜索或定位的引用。

教程确实只供某台受控机器或某个内部环境使用时，可以遵循该环境的明确约定；在交付说明中指出这一限制。

## 6. 验证与维护

- 验证本地相对链接存在，且没有越出预期项目边界。
- 抽查核心引用是否真的支持相邻结论，而不只检查目标可打开。
- 对无法访问的外部或内部链接，说明未验证的限制，不猜测其内容。
- 更新教程时重点复查入口、核心流程和高价值证据；行号仅在实际使用时检查漂移。
- 如果当前引用方式已不适合发布环境，转换为该环境支持的形式，而不是机械保留旧格式。
