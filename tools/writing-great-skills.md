## 简单介绍

github链接：[mattpocock/skills: Skills for Real Engineers. Straight from my .agents directory.](https://github.com/mattpocock/skills)

它把一个好 Skill 的目标定义为：

> 不是让每次输出完全相同，而是让 Agent 每次采用可预测的过程。

AI 技能可能变得冗长、模糊且难以调用。此技能提供编写和编辑高质量 Skill 的参考指南，涵盖核心词汇和原则，旨在确保 Skill 的可预测性与高效性。它帮助开发者优化 Skill 结构、管理上下文负载，并提升 AI Agent 执行任务的准确性和可靠性，从而构建更稳定、易于维护的 AI 应用。

```
## 调用方式

Skill 有两种调用方式，它们需要付出不同的成本。

- **模型调用型 Skill（model-invoked）**保留**** `****description****`****，因此 Agent 可以自主触发它，其他 Skill 也可以调用它；用户仍然可以手动输入 Skill 名称来调用。它会增加**上下文负载（context load）**，因为它的描述会在每一轮对话中出现在上下文窗口里。
    
    实现方式：不要设置 `disable-model-invocation`，并编写一段面向模型的描述，其中包含清晰、丰富的触发条件，例如：“当用户希望……、提到……时使用。”
    
- **用户调用型 Skill（user-invoked）**不会让 Agent 看到其描述。只有用户主动输入 Skill 名称时才能调用，其他 Skill 也无法调用它。
    
    它不会增加上下文负载，但会增加用户的**认知负载（cognitive load）**：你必须自己记得这个 Skill 存在，并知道什么时候应该使用它。
    
    实现方式：设置：
    
    ```
    disable-model-invocation: true
    ```
    
    此时 `description` 只面向人类，用一行概括 Skill 的用途即可，不需要列出大量触发条件。
    

只有当 Agent 必须自主找到这个 Skill，或者其他 Skill 必须调用它时，才应该选择模型调用型。

如果一个 Skill 永远只会被用户手动调用，就把它设计成用户调用型，从而避免上下文负载。

当用户调用型 Skill 多到你已经记不住时，可以使用一个**路由 Skill（router skill）**来解决累积的认知负载：创建一个用户调用型 Skill，在里面列出其他 Skill，以及它们分别应该在什么情况下使用。

## 编写 description

模型调用型 Skill 的 `description` 有两个职责：

1. 说明这个 Skill 是做什么的。
2. 列出应该触发它的不同**分支（branches）**。

描述中的每一个词都会增加上下文负载，因此，`description` 应该比 Skill 正文接受更加严格的删减。

### 将 Skill 的引导词放在最前面

把 Skill 最核心的**引导词（leading word）**放在描述开头。

`description` 是 Skill 完成自动调用匹配的地方，因此最关键的概念应该尽早出现。

### 每个分支只保留一个触发条件

如果多个表达只是同一个分支的同义改写，就属于**重复（duplication）**。

例如：

> 使用 TDD 构建功能……当用户要求测试优先开发时使用。

这里实际上把同一个触发分支写了两遍。

应该把它们合并，只保留真正不同的触发分支。

### 删除正文已经说明的身份信息

如果 Skill 的正文已经解释了它是什么，就不要在 `description` 中重复。

描述中只保留：

- 触发条件；
- 必要时，保留“当其他 Skill 需要……时调用”之类的可达性说明。

## 信息层级

一个 Skill 由两类内容组成：

- **步骤（steps）**
- **参考信息（reference）**

两种内容可以自由组合。一个 Skill 可以全部由步骤组成，也可以全部由参考信息组成，或者二者兼有。

核心问题是：

> 应该使用哪一种内容，以及这些内容应该放在信息层级的哪一层？

**信息层级（information hierarchy）**是一架梯子，根据 Agent 需要某项信息的即时程度进行排序。

### 1. Skill 内步骤

这是写在 `SKILL.md` 中、按顺序执行的动作，也是最主要的一层。

它描述 Agent 应该依次做什么。

每个步骤都应该以一个**完成标准（completion criterion）**结束，也就是告诉 Agent：满足什么条件时，这一步才算真正完成。

完成标准应该做到：

- **可检查**：Agent 能判断它究竟完成了还是没有完成。
- 必要时做到**穷尽**：必须覆盖所有目标，而不只是笼统地产生一个结果。

例如，应该写：

> 已说明每一个被修改的模型。

而不是：

> 生成一份修改清单。

模糊的完成标准很容易导致**过早完成（premature completion）**。

### 2. Skill 内参考信息

指直接写在 `SKILL.md` 中、供 Agent 按需查阅的定义、规则或事实。

参考信息有时天然就是一组平级规则。例如，代码评审中的每一条规则都位于同一层级。

这种扁平结构并不是问题，也不是代码坏味道。

当前这个 `writing-great-skills` Skill 就完全由参考信息组成。

### 3. 外部参考信息

把参考信息从 `SKILL.md` 移到独立文件中，并通过**上下文指针（context pointer）**引用。

只有当指针的触发条件满足时，Agent 才加载对应文件。

外部参考可以包括两种情况：

- **渐进披露的参考信息**：仍属于当前 Skill，例如同目录下的 `GLOSSARY.md`。
- 完全独立的**外部参考信息**：位于 Skill 系统之外，任何 Skill 都可以指向它。

严格的完成标准会推动 Agent 进行充分的**深入工作（legwork）**，也就是在任务内部真正开展调查、检查和验证。

这不取决于 Skill 是否包含步骤。

即使 Skill 只有一组平级规则，“每一条规则都已应用”这样的完成标准，也会像“每一步都已完成”一样约束 Agent。

向下拆出的内容太少，`SKILL.md` 顶层就会膨胀。

向下拆出的内容太多，又会隐藏 Agent 实际需要的信息。

如何平衡这两者，就是信息层级设计的核心。

### 渐进披露

**渐进披露（progressive disclosure）**，是指把内容沿信息层级向下移动：从 `SKILL.md` 移到被链接的独立文件中，让顶层文件保持清晰易读。

实现方法是：

- 在 Skill 目录中创建一个独立的 `.md` 文件；
- 文件名明确表达它保存的内容；
- 从 `SKILL.md` 中链接到该文件。

例如，当前 Skill 就把完整术语定义披露到 `GLOSSARY.md` 中。

部分 Skill 存在多种使用方式，每一种不同的执行路径都是一个**分支**。

分支是判断是否应该渐进披露的最佳标准：

- 每个分支都需要的信息，直接写在 Skill 中；
- 只有部分分支需要的信息，放到上下文指针之后。

决定 Agent 是否以及多可靠地访问某项信息的，并不是上下文指针指向了哪个文件，而是**指针本身的措辞**。

### 共置

信息层级决定一项内容应该放得多深。

**共置（co-location）**则决定：当它被放到某一层后，应该与哪些内容放在一起。

一个概念的：

- 定义；
- 规则；
- 限制和例外；

应该放在同一个标题之下，而不是分散在文件各处。

这样，Agent 在读取其中一部分时，也能同时看到与它紧密相关的内容。

## 什么时候应该拆分 Skill

**粒度（granularity）**描述 Skill 被划分得有多细。

每一次拆分都会增加上下文负载或认知负载中的一种，因此，只有当拆分带来的价值足以覆盖成本时，才应该拆分。

主要有两种拆分方式。

### 按调用方式拆分

当存在一个独立的**引导词**，应该让 Agent 根据它自动触发某项能力，或者其他 Skill 必须调用该能力时，可以把它拆成一个独立的模型调用型 Skill。

这样做会产生新的上下文负载，因为新 Skill 的 `description` 会始终存在于上下文中。

因此，这种独立可达性必须确实值得付出成本。

### 按执行顺序拆分

当一个 Skill 包含连续的多个步骤，而 Agent 因为已经看到后续步骤，倾向于仓促完成当前步骤时，可以按执行顺序拆分。

一个步骤完成之后才能执行的后续步骤，称为该步骤的**完成后步骤（post-completion steps）**。

提前展示这些步骤，可能让 Agent 把注意力放在“赶紧进入下一步”上，从而发生过早完成。

把后续步骤暂时隐藏起来，可以促使 Agent 在当前任务上投入更多深入工作。

## 删减

每一个含义都应该只有一个**单一事实来源（single source of truth）**。

也就是说，一个行为只在一个权威位置定义。这样，修改行为时只需要改一个地方。

检查 Skill 中的每一行是否具有**相关性（relevance）**：

> 这句话现在是否仍然会影响这个 Skill 的行为？

然后逐句寻找**无效指令（no-op）**，而不只是逐行检查。

将每一个句子单独拿出来执行无效指令测试：

> 与模型默认行为相比，这句话是否真的改变了 Agent 的行为？

如果没有改变，就删除整个句子，而不是仅仅压缩它的措辞。

应该果断一些：大多数未通过测试的文字都应该被删除，而不是重新改写。

## 引导词

**引导词（leading word）**是一个已经存在于模型预训练知识中的紧凑概念。

Agent 在执行 Skill 时，可以使用这个概念来组织思考。

例如：

- lesson
- fog of war
- tracer bullets

一个引导词可以在文本中反复出现，但不一定必须重复；足够强的引导词可能只出现一次就能发挥作用。

随着它在 Skill 中被使用，它会逐渐形成一种分布式定义，并利用模型已经掌握的先验知识，用尽可能少的 Token 锚定一整片行为模式。

引导词通过两种方式提高可预测性。

### 在正文中锚定执行

每当引导词出现时，Agent 都会倾向于调用相同的行为模式。

### 在 description 中锚定调用

当同一个引导词同时出现在：

- 用户提示词；
- 项目文档；
- 代码；
- Skill 的 description；

Agent 就更容易把这些共同语言与对应 Skill 联系起来，从而更可靠地触发它。

应该主动寻找机会，用引导词重构 Skill。

例如：

- 同一个三元概念在三个地方被完整写出，形成了重复；
- 一整句话只是在间接描述一个概念；

这些地方都应该尝试**折叠（collapse）**成一个词。

例如：


“快速、确定、低开销”
→ tight


这里把一个阶段中反复出现的三种性质，折叠成模型已经理解的一个词，例如：

> 一个 tight 的反馈循环。

又如：


“一个你能够信任的循环”
→ red


`red` 把模糊的判断标准转化成一个二元、可观察的状态：

- 这个循环能在 Bug 出现时变红；
- 或者它不能。

这样做可以获得双重收益：

- 使用更少的 Token；
- 为 Agent 提供一个更清晰的思维抓手。

应该假设每个 Skill 中都存在可以被引导词取代的重复解释，并主动找到它们。

## 失败模式

可以使用以下模式，诊断用户在使用 Skill 时遇到的问题。

### 过早完成

**过早完成（premature completion）**是指一个步骤还没有真正完成，Agent 就结束了它，把注意力转向“完成整个任务”。

防御方式按以下顺序执行：

1. 首先强化完成标准。这种修改成本低，而且影响范围局部。
2. 只有当完成标准本身无法进一步明确，并且已经观察到 Agent 确实在赶进度时，才通过拆分 Skill 隐藏完成后步骤。

### 重复

**重复（duplication）**是指同一个含义出现在多个地方。

它会：

- 增加维护成本；
- 浪费 Token；
- 让某个含义在信息层级中的突出程度超过其实际重要性。

### 沉积

**沉积（sediment）**是指陈旧内容不断堆积。

它产生的原因是：

- 增加内容让人感觉安全；
- 删除内容让人感觉有风险。

如果一个 Skill 没有明确的删减纪律，沉积就是它默认的最终命运。

### 蔓延

**蔓延（sprawl）**是指一个 Skill 单纯变得过长，即使里面每一行都仍然有效且没有重复。

它会：

- 降低可读性；
- 降低可维护性；
- 浪费 Token。

解决方法是利用信息层级：

- 把参考信息放到上下文指针之后；
- 按分支或执行顺序拆分；
- 让每条执行路径只携带它真正需要的信息。

### 无效指令

**无效指令（no-op）**是指模型本来就会默认遵守的一句话。

你为它支付了上下文负载，但它没有带来任何行为改变。

判断标准是：

> 与默认情况相比，这句话是否改变了 Agent 的行为？

例如，模型本身通常已经会进行一定程度的检查，因此：

> 要彻底一些。

可能是一个无效指令。

解决办法不是换一种技巧，而是使用更强的引导词，例如：

> 要进行不依不饶的检查。

也就是用 `relentless` 替代较弱的 `thorough`。

### 否定式指令

**否定式指令（negation）**通过禁止某种行为来引导 Agent，但经常适得其反。

例如：

> 不要想一头大象。

这句话仍然主动提到了“大象”，反而让这个概念在模型中变得更容易被想到。

应该优先使用**正向指令**：

- 直接描述目标行为；
- 尽量完全不提不希望出现的行为。

只有当某项禁止要求是无法改写成正向表达的硬性护栏时，才保留否定式指令。

即使如此，也应该同时告诉 Agent：

> 不应该做什么，以及应该改为做什么。
```

## 已更新为writing-for-agents

> 作者官方声明：
> Where did `/writing-great-skills` go? It is this skill（writing-for-agents）, renamed in v1.1.

改名原因：作者发现，这个 Skill 讲的东西其实**不只适用于写 Skill**。

所以把名字扩大成了 **`writing-for-agents`**。现在官方介绍也是：
> “the reference you write agent-facing documents against”

也就是可以理解为：

**以前：怎样写好 Skill**  
↓  
**现在：怎样写好「给 Agent 看的指令/文档」**

新版覆盖的是“**any document an agent consumes**”，旧版的 `GLOSSARY.md` 被合并进主体，而 frontmatter、model/user invocation、router skill 等真正只属于 Skill 的机制则被拆到 `SKILL-MECHANICS.md`。同时旧名字直接删除，没有 alias。

| 对比项             | 旧版 `writing-great-skills`                     | 新版 `writing-for-agents`                               |
| --------------- | --------------------------------------------- | ----------------------------------------------------- |
| 核心对象            | 专门写 **Skill**                                 | 写一切 **Agent-facing documents**                        |
| 适用范围            | `SKILL.md`                                    | `SKILL.md`、`AGENTS.md`、`CLAUDE.md`、被 pointer 引用的文档    |
| 调用方式            | **user-invoked**，需要主动 `/writing-great-skills` | **model-invoked**，编辑 Skill / AGENTS.md 等时 Agent 可自行触发 |
| 核心文件            | `SKILL.md + GLOSSARY.md`                      | `SKILL.md + SKILL-MECHANICS.md`                       |
| Skill 特有知识      | 混在主体中                                         | 单独抽到 `SKILL-MECHANICS.md`                             |
| 核心抽象            | “怎么设计一个好 Skill”                               | “怎么设计 Agent 消费的上下文”                                   |
| context pointer | 主要理解成 Skill description / 引用                  | 泛化为所有“上下文→外部信息”的指针                                    |
| 信息层级            | in-skill step / reference                     | in-file step / reference，更通用                          |
| 新增思想            | —                                             | environment 也是 source of truth；文档可能只是一个 **cache**     |


个人理解：  
一个 Skill、AGENTS.md、CLAUDE.md、或者某个被引用的 markdown，本质上都是 Agent 消费的 context。  
写skill某种程度上就是写提示词，视角往上提一层，研究的问题变成：怎么给 Agent 写信息，才能让 Agent 稳定地在正确时机获得正确上下文，并采取正确流程。  
所以新的这个skill更偏向现在经常讲的 Context Engineering，而不只是 Prompt/Skill 编写技巧了。  

所以可以把之前的旧版skill给扔掉，用新版了，完全的上位替代。毕竟就连作者都没保留原版，而是在原版上升级和修改。

## 和`skill-creator`配合

可以配合使用，但**不要让两者重复负责同一件事**。最合适的关系是：

> **`skill-creator` 负责把 Skill 创建出来；`writing-great-skills` 负责审查它是不是一个设计良好、行为可预测的 Skill。**

```
skill-creator
├─ 创建
├─ 初始化
├─ 生成资源
├─ 格式校验
└─ 迭代

writing-great-skills
├─ 调用设计审查
├─ 信息层级审查
├─ 完成标准审查
├─ 精简与去重
└─ 失败模式诊断
```


日常不需要每次写很长的提示词，可以直接这样调用：

```
先使用 skill-creator 创建或更新这个 Skill，
再使用 writing-great-skills 对它进行设计审查，
最后回到 skill-creator 应用修改、测试脚本并完成格式校验。

以当前运行平台的 Skill 格式规范为准。
不要把 writing-great-skills 的平台专属 frontmatter 直接复制过来。
```

两者组合后依然不能取代 Eval：它们能帮助你写出**结构合理的 Skill**
